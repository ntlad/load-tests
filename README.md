# Домашнее задание №4: нагрузочное тестирование REST API

## Запуск

Нужны JDK 17, Maven 3.6.3 или новее и Apache JMeter 5.6.3.
JMeter устанавливается отдельно из [бинарного архива Apache](https://jmeter.apache.org/download_jmeter.cgi).

Если на macOS JMeter распакован в `~/Downloads/apache-jmeter-5.6.3`, настроить
текущий терминал:

```bash
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"
export PATH="$JAVA_HOME/bin:$HOME/Downloads/apache-jmeter-5.6.3/bin:$PATH"
mvn -version
jmeter --version
```

Maven должен использовать Java 17. На других системах добавить JDK 17 и
каталог `bin` установленного JMeter в `PATH`.

Из корня проекта собрать и запустить API:

```bash
mvn package
java -jar target/load-tests-api.jar
```

Сервис запускается на `127.0.0.1:8080`. Терминал с сервисом оставить открытым,
команды JMeter выполнять в другом терминале. Для остановки API нажать `Ctrl+C`.

## Используемый API

Локальный REST API написан на Java 17 с использованием встроенного HTTP-сервера.
Класс сервиса находится в [src/main/java/LocalApiServer.java](src/main/java/LocalApiServer.java).
Запросы обрабатываются восемью потоками. Данные формируются в памяти,
без базы данных и внешних сервисов.

- `GET /health` - HTTP 200 и состояние сервиса.
- `GET /api/items/{id}` - HTTP 200 и данные товара, ID от 1 до 100.
- Несуществующий ID или неизвестный путь - HTTP 404.
- Метод, отличный от GET, - HTTP 405.

В другом терминале проверить API:

```bash
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/api/items/1
```

Ожидается HTTP 200. Для товара с ID 1 возвращается:

```json
{"id":1,"name":"Item 1","price":101}
```

## Сценарии JMeter

Подготовлены два сценария:

1. **Базовая проверка:** `jmeter/basic-api-test.jmx` выполняет один запрос
   `GET /api/items/1`. Проверяются HTTP 200 и значение `$.id`, равное 1.
   В Thread Group задан один пользователь, ramp-up 1 секунда и одна итерация.
2. **Нагрузочный сценарий:** `jmeter/api-load-test.jmx` выполняет запросы
   `GET /api/items/${itemId}`. ID берутся из `data/items.csv`. Проверяются
   HTTP 200 и соответствие `$.id` значению `${itemId}`.

В CSV находятся заголовок `itemId` и идентификаторы от 1 до 10. Файл общий для
всех потоков, после последней строки чтение начинается сначала. Путь к CSV
задан относительно файла `.jmx`, исправлять его после скачивания проекта не нужно.

Constant Timer задаёт паузу 1000 мс перед каждым запросом, включая первый.
Таймауты соединения и ответа - 5000 мс.

Для проверки базового сценария открыть JMeter:

```bash
jmeter -t jmeter/basic-api-test.jmx -j target/jmeter-gui.log
```

Нажать `Run -> Start`. В `View Results Tree` ожидается один успешный запрос
с HTTP 200 и JSON товара с ID 1.

Нагрузочный сценарий можно открыть отдельно:

```bash
jmeter -t jmeter/api-load-test.jmx -j target/jmeter-load-gui.log
```

Без профиля нагрузки он выполняет три итерации одного пользователя:
ramp-up 1 секунда, ограничение времени 15 секунд. Для просмотра ответов
временно включить `View Results Tree (debug only)`. Ожидаются товары с ID 1, 2
и 3. После проверки отключить Listener и сохранить сценарий через `File -> Save`.
Во время основных запусков `View Results Tree` должен быть отключён.

## Профили нагрузки

Параметры запусков находятся в папке `profiles/`:

| Файл | Пользователи | Ramp-up | Длительность | Think time |
|---|---:|---:|---:|---:|
| `10-users.properties` | 10 | 10 с | 120 с | 1000 мс |
| `25-users.properties` | 25 | 10 с | 120 с | 1000 мс |
| `50-users.properties` | 50 | 10 с | 120 с | 1000 мс |

Во всех профилях `loops=-1`: запросы выполняются до окончания заданного времени.
120 секунд включают ramp-up. Между запусками меняется только число пользователей,
остальные настройки сценария и сервиса одинаковые.

## Запуск нагрузки и HTML-отчёт

При работающем API из корня проекта выполнить по очереди:

```bash
bash scripts/run-load.sh 10
bash scripts/run-load.sh 25
bash scripts/run-load.sh 50
```

Перед следующей командой дождаться завершения предыдущей. Каждый запуск занимает
около двух минут плюс время на создание отчёта.

Скрипт запускает JMeter из `JMETER_HOME`, из `PATH` или из
`~/Downloads/apache-jmeter-5.6.3`. Профиль передаётся через `-q`, результаты
сохраняются через `-l`, HTML-отчёт создаётся через `-e -o`.

Для каждого запуска создаётся отдельная папка в `results/`:

- `profile.properties` - использованные параметры нагрузки.
- `results.jtl` - результаты запросов в CSV-формате.
- `console.txt` - вывод запуска с итоговой строкой `summary`.
- `html-report/` - HTML-отчёт со статистикой и графиками.
- `jmeter.log` - журнал JMeter, исключён из Git.

При повторном запуске предыдущие результаты сохраняются. Успешный запуск JMeter
сам по себе не означает, что запросы прошли проверки: ошибки видны в строке
`summary` и в HTML-отчёте.

В папке с результатами `results` нужного запуска открыть `html-report/index.html` в браузере.
Для просмотра отчёта нужны все файлы из `html-report/`.
Графики по времени строятся с шагом 5 секунд.

## Результаты

Проведены три запуска 10 ноября 2026 года. Среда: macOS 15.2, ARM64,
OpenJDK 17.0.15, JMeter 5.6.3. API и генератор нагрузки работали на одном компьютере.

Показатели взяты из строки `Total` HTML-отчётов и сверены с JTL.
Время ответа и перцентили указаны в миллисекундах.

## Вывод

При увеличении нагрузки с 10 до 50 пользователей Throughput вырос примерно
в пять раз, с 9.64 до 48.02 RPS. Среднее время ответа снизилось с 1.12 до 0.55 мс,
медиана осталась равной 1 мс. p95 не увеличился: 2 мс, 2 мс и 1 мс.

Все 9704 запроса завершились с HTTP 200 и прошли проверки ответа. Ошибок нет.
Момент, когда Throughput перестаёт расти, а время ответа или число ошибок
увеличиваются, не обнаружен. Диапазон 10-50 пользователей с паузой 1 секунда
в условиях этого эксперимента можно считать стабильным. Предел производительности
сервиса не определён.

На каждом уровне выполнен один прогон. API работает с данными в памяти, без БД
и внешних сервисов. Отдельно влияние прогрева JVM не проверялось, поэтому
снижение среднего времени ответа не означает, что нагрузка ускоряет сервис.
Значения 0 мс в JTL связаны с точностью записи времени в целых миллисекундах.
Вывод относится к этому локальному стенду и выбранному профилю нагрузки.

Скриншоты выполненных проверок находятся в папке [checks](checks/).
